# מרווח frontend

Implementation date: 2026-10-16. This React/TypeScript frontend is a Hebrew RTL demonstration using entirely invented adults and sessions. The root README and operating handbook describe deployment and server configuration.

## Start and configuration

Run the root package's `npm run dev`, `npm run typecheck`, or `npm run build`. Vite's application root is this directory. `VITE_API_URL` sets the API origin; an empty value uses same-origin `/api/`. `PAGES_BASE`, handled by the root Vite configuration, sets the static site's base path. Handbook links use `import.meta.env.BASE_URL` so they work below a GitHub Pages repository path.

The browser never receives provider or database credentials. `/api/access` accepts the private code and returns a one-hour bearer token kept in React memory only. That token can authorize live inference and the separate shared-workspace connection. `/api/turn` and `/api/draft` receive the shared `ModelRequest`; `/api/workspace` reads or saves the full fictional archive. A model selection change applies to the next inference request and does not create a second patient memory.

## Interface structure

- `App.tsx`: state loading and saving, case/session/branch selection, prepared or live requests, conversation, session drafting, approval, settings, import/export, and preference editing.
- `NewPatient.tsx`: display name/code and optional recurring weekday/time only; opens a new fictional record at session 1.
- `workspace-sync.ts`: explicit remote read, validated responses, serialized snapshot saves, and revision-based conflict detection; pauses on failed or uncertain saves.
- `workspace-choice.ts`: pure reconnect decision for empty/equal, clean-local, and divergent states.
- `RecoveryCopies.tsx` and `packages/domain/recovery-storage.ts`: list/export separate page-writer recovery snapshots without switching the active state or deleting stored entries.
- `Documents.tsx`: direct editing of the note and four cumulative products, 32 intake fields and nine report sections, full-version comparisons and restoration, and explicit acceptance or rejection of proposals.
- `Backstage.tsx`: actual prompt, actual context, structured response and request metrics, and explicitly labeled prepared instruction examples. Includes online handbook and PDF entry points.
- `ui.tsx`: accessible native dialogs, document rendering, copying, source viewer, and provenance labels.
- `styles.css`: typography, layout, RTL, mobile behavior, visible keyboard focus, and reduced-motion support.
- `DESIGN.md`: design decisions and brief review.
- `public/handbook.html` and `public/handbook.pdf`: maintained by the integration owner, not generated by the frontend.

The interface imports all context, version, source, and branch behavior from `packages/domain`. It imports the same prompt builder that the API uses. Prepared responses come from `fixtures/fictional/prepared.ts`; they never pretend to be fresh model output.

## Session states and interaction

The first fixture-based run opens the first illustrative patient at session 5, retaining sessions 1–4 for context and comparison. **New record** requires only a fictional display name/code and optional recurring weekday/time. `createPatient` creates a separate root branch and session 1, with no prior clinical history. The schedule is administrative planning, not proof that a session occurred; there are no calendar reminders or additional onboarding questions. Selecting another existing patient opens its latest session on its root branch and does not create session 5 or any new session. Later sessions are explicitly created through the new-session control.

The writing state permits several contributions before the clinician chooses to finish sharing. Enter inserts a newline. Ctrl/Cmd+Enter sends the current contribution. The question state supports an answer, skipping, and unconditional drafting. The domain enforces the three-question ceiling. Optional intake begins only by explicit action after a draft, resets its two-question counter, and increments its round; another round requires another explicit action. A provider error retains source text and offers a clearly labeled manual draft.

Approval is explicit. Later edits create new document versions. The domain protects manual/approved content through proposals; the interface shows the proposal beside the current version and requires an explicit accept/reject decision. Version restoration creates a new version, leaving previous versions intact. Every source viewer uses structured source IDs and shows the original stored text.

## State, persistence, and stale responses

The full `PortalState` is stored through the shared IndexedDB adapter after a 450 ms debounce. Local writes are serialized. **נשמר בדפדפן הזה** appears only after the corresponding local write succeeds. Failure is reported; JSON export remains available. A public visitor starts with this local copy and no automatic server connection.

**פתיחת התיקים השמורים** explicitly authenticates and loads the single owner workspace. The private code grants access to every fictional record in that workspace, with no separate accounts or per-record permissions. Storage connection and prepared/live mode are independent: prepared mode can save remotely without inference, and entering live mode alone does not connect storage. The token is lost after a reload and expires after one hour, so reconnect explicitly. GitHub Pages and Vercel keep different browser-local copies but can reach the same workspace when configured with the same API.

Once connected, changed state is queued for a `PUT` carrying `expectedRevision`. Only the latest pending snapshot needs to be sent; writes do not overlap. **נשמר במאגר** means the current snapshot received a successful server acknowledgement, not merely that the HTTP request started. The server retains the latest full snapshot, including its existing document versions and sources; it does not keep every previous snapshot or every keystroke. The server request limit is 3,000,000 bytes, distinct from the larger local-import limit. There is no background polling or real-time collaborative merge.

Reconnect reads the server first and compares it with the local state and the last confirmed base. The base is tab-scoped in `sessionStorage`; another tab cannot advance this tab's assumed revision. Automatic activation occurs only for an empty workspace or equal local and remote states. A clean local state matching its last confirmed base can adopt a newer remote state; dirty differing local work requires an explicit choice even when the server revision still matches the old base. Offline edits are not automatically uploaded or merged on reconnect. Before adopting a different server state, the application preserves one previous local snapshot under `before-cloud-load` in IndexedDB. The settings action **ייצוא העותק שלפני הטעינה מהמאגר** exports it. A later server adoption replaces that recovery slot; it is not an external backup. Unsaved direct-document edits must be saved before switching copies.

HTTP 409 pauses writes rather than overwriting another browser. Authentication expiry also pauses and clears the token; network errors, timeouts and oversized saves are visible. Work remains local when possible. Export the current state, reconnect/read the server, and reconcile deliberately; do not silently change the expected revision or retry as if the earlier write certainly failed. A response can be lost after a successful save. The UI offers reconnect and export, and does not continuously retry failures. Disconnect stops remote writes, clears the access token, returns to prepared mode, and retains both the local copy and the server record.

On an actual sync error/conflict/auth pause, and on further state changes while `cloudError` remains, the application also preserves a separate `unsynced:<page-writer-id>` snapshot in IndexedDB. This is independent of the shared `current` key and the single `before-cloud-load` slot. A different tab cannot overwrite this page's key. The settings recovery list shows timestamps and counts, exports readable copies without changing active state, and retains unreadable entries. It does not capture every healthy visit or every keystroke and does not prove server saving. Copies are not automatically deleted; if local recovery saving fails, the UI directs the user to export manually before leaving.

Conversation composer text belongs to its session and is part of the persisted state. Direct document edits require the visible save action and remain in a page-memory edit cache while changing views; they are not yet saved versions and are labeled accordingly. Reloading before saving a direct edit loses that unsaved edit. JSON export contains saved state and full versions, not those unfinished direct edits or access credentials.

Switching session, branch, mode, or model cancels an active request. Cancellation ends the browser's wait; it does not promise cancellation of provider billing. Each response is checked against the initiating request, session, session revision, document versions, and preferences. A response arriving after those change is not applied. Typing an unsent new composer contribution does not overwrite or erase it when a request completes.

## Prepared and live limitations

Prepared mode is deterministic. It preserves entered material and offers illustrative questions, but does not perform unrestricted language-model extraction or clinical inference. Backstage instruction comparisons are authored examples, not measured model experiments. Live inference requires a configured server and valid access code. Server quota, validation, and provider behavior are separate from frontend availability.

JSON import replaces demo state after schema validation and confirmation. Reset restores the invented fixtures after confirmation. If storage is connected, the replacement is also queued to the shared workspace; the confirmation states this explicitly. Export before replacement. Branching uses the shared domain's time-bound inheritance. Server persistence remains a fictional single-owner demo, not a clinical deployment, a multiuser permissions system, or an independent backup history.

## Verification boundary

Type checking and bundling can verify integration shape. They cannot establish rendered behavior. The integration owner must load the finished application as a participant in a browser and check desktop and mobile flows, minimal record creation, session continuation, version/source controls, optional intake, cancellation, import/export, and handbook/PDF links before claiming delivery. Workspace acceptance additionally needs two independent browser contexts, explicit reconnection after reload, confirmed remote persistence, retained versions, conflict and outage behavior, and recovery-copy export. Current results belong in the dated release evidence, not an unqualified claim in this architecture document.
