# Documentation assistant prompts

Prompt version: 2026-10-16.13. This assistant supports documentation after each adult session and maintains five related case documents through one conversation. It is not a patient simulation, clinical supervisor, assessment instrument or treatment recommender. Hebrew and clinician-attributed interpretation are explicit requirements.

## Composition

The authoritative editable source is [PROMPTS.md](../../Prompt_Workbench_2026-10-16/PROMPTS.md). Its sixteen named BEGIN/END blocks contain the version, all eleven sections with editable headings, both output contracts, request-control template and final assembly template. Author notes outside the blocks are not model instructions. Fixed machine placeholders insert the canonical intake schema and request controls; no case material belongs in the authoring source.

After editing, run `npx tsx scripts/sync-prompts.ts`, then `npx tsx scripts/sync-prompts.ts --check`. The first command validates the source and deterministically generates authored.generated.ts; the second checks source/runtime parity without writing. Missing, duplicate, malformed, nested and unknown blocks, invalid headings, and missing/unknown/repeated placeholders fail validation. Do not hand-edit the generated module. Commit the source and generated changes together. Tests, a new build and deployment are still required to change the deployed assistant; editing Markdown alone does not update an existing deployment.

index.ts exports PROMPT_VERSION, readable PROMPT_SECTIONS, PROMPT_TEMPLATES and buildSystemPrompt(context, task). PROMPT_TEMPLATES exposes turnContract, draftContract, requestControl and assembly for inspection. The runtime imports only generated data and a one-pass interpolation helper; it never reads authoring files or evaluates their contents as code. Inserted values are not recursively interpreted as placeholders. The compiler and filesystem operations remain in scripts/prompt-source.ts and scripts/sync-prompts.ts.

The builder selects the task contract and assembles control metadata separately from source/message/document/preference prose, which travels as JSON context data. Editing behavior wording does not change the code that selects admissible context, the output validator, or the question counters. Changes to those interfaces require coordinated code changes. The handbook imports the active runtime instructions and generated contracts.

intake-schema.ts owns 32 fields, nine sections, statuses and the report renderer. Domain code owns scope, provenance, staging, approval, versions and import validation. Prompt code does not import domain code.

## Behavior

Each contribution receives a real model response. A useful follow-up resolves one concrete documentation gap in the latest contribution, with permitted history. It is one open question, not a generic request to repeat what matters, a checklist, a leading interpretation or clinical advice. Prior assistant text provides conversational context, never proof that its premise occurred.

The main flow permits zero to three questions; the ceiling is not a target. Stop/lack of time/draft requests move to drafting. Explicit expansion uses focusGoal/focusSelection and at most two questions. A genuinely missing part of the explicitly selected intake topic may itself anchor one neutral documentation question, even without a link to the latest session narrative. The topic selection is permission to clarify, not factual evidence. Existing sources and pending fields must be checked first; partial fields invite only the missing part, and documented/not-applicable fields are not reopened. A new round does not override blocked/skipped topics or failed recall. If no permitted question is grounded, leave the field missing rather than inventing a connection. A skip alone is a process choice, not evidence of failed recall or absent assessment. Quoted patient speech is not an instruction from the clinician to the application.

The note is primary. Each contribution is also considered for relevant additions to the other four documents: formulation organizes the clinician's hypotheses; intake accumulates sourced fields; learning retains moments the clinician identified; supervision organizes stated uncertainties without answering them. From session 4, intake gaps receive more attention during the actual conversation when a short, relevant follow-up can help within the existing main allowance. Unrelated background is not introduced into main solely because of the session number. Case management here means organizing documentation, not directing treatment. No diagnosis, intervention, agreement, signature or negative risk finding is invented.

less, block and exclude reduce question priority, prevent questions and omit material from a specified output respectively. None deletes sources. Both turn and draft tasks extract new explicit preferences and apply them in that same response, including direct drafting and exhausted question budgets. Already recorded preferences are not emitted again. Session preference is the default; persistence requires explicit intent. Code checks structural and lexical parts; meaning still requires review.

## Working memory and output

documents contains saved versions and, when available, author/approval/time/reason metadata. workingDraft is the unapproved derived proposal; workingDraftMetadata identifies its bases and whether it is stale. pendingIntakeFields is the working ledger. Rewriting checks the proposal against current documents and sources; approval metadata is not factual validation. Missing legacy metadata must not be guessed. Style commands are not clinical events. The assistant cannot claim to save or approve documents.

Each summary is rebuilt from the current response's source-checked note and document changes, compared only with saved context.documents. A prior proposal remains an editing base, not a saved comparison baseline; a document absent from saved context is described as new even when copied from that proposal. It explains in plain Hebrew what the note proposes and where other relevant changes go, using document names rather than internal keys or field IDs. It describes changes as awaiting review/approval and never claims all five documents changed when only some did. Adding attributed factual detail is a change even when no new formulation hypothesis is introduced; such a document must not be described as unchanged. Prior summary/rationale text stays available for explicit relative edits, but is not evidence or a template to copy. An unsupported AI-draft claim should be corrected even when the clinician requests only a stylistic edit. This instruction reduces a known error path; it does not guarantee semantic fidelity.

Turn output contains action, utterance, topic, rationale, fieldUpdates and preferenceUpdates. Draft output contains five distinct documents, sparse fieldUpdates, preferenceUpdates, rationale, summary and zero to three followUps. These are optional invitations/reminders, not required questions. The review interface calculates its prominent change summary from the actual proposal and saved baselines; the model's original summary remains available in the response record for inspection. This prevents an unsupported model claim about new versus unchanged documents from determining the approval explanation.

The model returns empty intake document content/citations and only changed fields. The domain merges existing, pending and new fields, derives sources and renders all nine sections. From session 4, a defined actual gap may receive an optional expansion invitation; session 4 may also receive a short reminder for session 5. Session 5 always gets the full structure, without falsely declaring unknown information complete. Completion is not a condition of approval. A lack-of-time request receives no expansion invitations.

Before returning field updates, the prompt requires a coverage check across all 32 fields against admissible explicit sources and the current working ledger. Sparse updates omit unchanged fields; they must still include a relevant empty/unknown field when explicit source evidence already supports it, including evidence from earlier sessions or evidence applicable to more than one field. Partial evidence remains partial, exclusions still apply, and the check does not authorize more questions or inferred facts. Field 5 is the explicitly stated reason for seeking care; field 6 is the patient's reported complaint; field 8 describes the current problem and any documented course. A complaint alone does not establish the reason for seeking care. Administrative details also require explicit sources and cannot be inferred from login names, internal identifiers or execution timestamps.

A later direct clinician edit takes precedence over older material when the field itself cites a manual source recording its revised or emptied state. Coverage must not restore that removed text without a new explicit instruction or substantive source. A blank field or clinician authorship of the whole report alone does not establish deliberate field removal.

Unknown fields require an empty value; a description of missing information belongs in remaining. The provider's output schema expresses this with nested anyOf branches: unknown requires the empty-string enum, while the other statuses allow text. Runtime validation remains active; rejected content is never silently emptied or relabeled. Historical context fields keep their existing schema. Every other status requires at least one existing source ID, including explicit non-assessment and failed recall. Failure to remember exact wording does not erase content the clinician has described. These constraints do not explain any historical failure whose response was not retained.

Context projection removes exact duplicated report rendering only when the structured ledger retains the information. Raw sources and messages are not truncated. All source timestamps, including current-session sources, must fit asOf; there is no current-session cutoff exception. Citations must cover every factual contribution to a field.

rationale explains the observable relation between input and result in one or two sentences. It is not hidden reasoning or proof of fidelity. The interface exposes it on request alongside exact context and citations.

## Verification and maintenance

Relevant suites: prompt-authoring.test.ts, prompts.test.ts, prompt-behavior.test.ts, staged-records.test.ts, context-budget.test.ts and API tests. Authoring tests verify source/runtime parity (including drift failure), marker errors, canonical schema interpolation, one-pass substitution and editable-source effects. The historical prepared fixture remains for compatibility/tests; new chat never calls it. Passing deterministic tests is not live-model verification.

Review fictional conversations covering sparse input, a concrete event, attributed hypotheses, correction, stop, forgotten detail, blocked topic, contradiction and incomplete session-five intake. Also distinguish initial generation, regeneration from an erroneous AI summary, and explicit correction; test relative summary edits, skip versus failed recall, and preferences introduced during direct drafting. Preserve supported complaint coverage without inventing a referral reason, completion of a previously omitted field from an existing source, retained unsupported gaps, and accurate descriptions of factual additions. For .13, compare main-flow narrative grounding against explicitly selected missing-field grounding, session-4 intake awareness, refusals/time limits, and plain-language summaries of changes across documents. Record actual results and limits. Behavioral changes require a prompt-version update in the Markdown source, synchronization, tests and regeneration of both handbook formats. Development history belongs in Implementation_2026-10-16/progress.md; this document describes the current system.

The design adapts CPE's fixed behavior, dynamic process and context layers without simulated hidden mental states, participant scoring or clinical direction. Sources are the approved master plan, contextual-question examples, contracts and actual code. No real patient/client/participant material is used.
